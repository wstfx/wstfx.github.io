01 / From a checkpoint to a moving vehicle

The loop is part of the experiment.

A vision-language-action (VLA) model takes visual observations and driving context and predicts what the vehicle should do next. Testing it in a simulator requires every part of that exchange to agree: what the cameras see, when history is sampled, how a trajectory is represented, and how the controller executes it.

At Dongfeng, I worked on that connection. I debugged the ONNX integration in Bench2Drive/CARLA, built a driver for direct PyTorch inference, and connected the T3 model to AlpaSim and OmniDreams. I also tested Apollo and 51Sim to explore commercial simulation workflows.

02 / Make the inputs and outputs mean the same thing

Repairing the interface.

I traced problems in the ONNX path across trajectory shapes, coordinate conventions, navigation commands, and temporal sampling. A trajectory can be numerically valid and still tell a controller to move in the wrong direction. I corrected those mappings and aligned camera history with ego-vehicle history in simulation time.

I also found redundant multi-gigabyte array copies in the inference path. Removing them reduced a major source of overhead and made repeated evaluation more practical.

What the recorded latency measurements show

The route-level records report approximately 68 seconds of baseline mean latency and 5.7 seconds of optimized warm-state median latency. The statistics and operating conditions differ, so these describe the measured runs rather than a universal speedup ratio.

03 / Keep the model ready for the next step

Native inference. A synchronized loop.

To run the model directly in PyTorch, I separated the simulator and model into their own Python environments. A persistent inference service loads the checkpoint once, while a bridge handles the exchange with CARLA. Images and metadata travel through a shared directory; Unix Socket messages coordinate each request and response.

Each model request combines seven cameras × three frames with ego history and navigation. The bridge checks request IDs, timestamps, and the returned 32-point trajectory before converting coordinates for the controller. When a new action is needed, simulation waits for inference; intermediate ticks hold the previous control.

I made evaluation restartable and separated driving outcomes from infrastructure faults. In one documented 20-route subset, 17 routes produced scores and videos; three failed in rendering before the first frame. That distinction prevents a simulator failure from being mistaken for a model result.

04 / A second simulation environment

Connecting T3 to AlpaSim.

I then built the T3 adapter and gRPC Driver connection for AlpaSim. OmniDreams renders the scene, AlpaSim assembles image and vehicle history, and T3 predicts future trajectory points. The controller and physics update the vehicle’s pose, which determines the next rendered view.

These approximately 20-second recordings use a single front camera, while the checkpoint was trained with seven cameras. They validate the engineering connection under that input mismatch; they are not a final model-quality benchmark.

I documented how to replace compatible checkpoints, start the Driver, run a closed-loop scene, and generate videos and metrics. The guide also makes the model’s image-history, trajectory, and coordinate requirements explicit, so a checkpoint change can be checked before a long run begins.

05 / Looking beyond the custom pipeline

Testing commercial simulation workflows.

Alongside the model integrations, I tested Baidu’s Apollo platform and 51Sim. These gave me another view of the simulation workflow: inspecting multi-camera playback and evaluation traces in Apollo, and working with scenario construction and traffic-participant behavior in 51Sim.

06 / Leave behind something others can run

From a working demo to a reusable workflow.

I consolidated the work into the team’s VLA development Wiki: ONNX debugging and integration notes, a Bench2Drive/CARLA guide for native PyTorch inference, and a T3–AlpaSim checkpoint and Driver guide. Together with resumable evaluation and recorded rollouts, these gave the team a path to repeat the experiments and investigate failures.

What I took from the work

A useful evaluation system makes a model’s behavior inspectable. Correct inputs, synchronized execution, and clear failure records are what let the next experiment answer a real question.
